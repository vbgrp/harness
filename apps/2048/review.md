# 2048 게임 웹앱 — Review 결과

Build 서브에이전트와 독립적으로 `spec.md` 요구사항 대비 `index.html` / `style.css` / `script.js`를 코드 리뷰하고, 로컬 정적 서버(`python -m http.server`)로 실제 브라우저(Claude Browser pane)에서 기능을 직접 테스트했다.

## 테스트 방법
- `apps/2048` 폴더에서 임시 정적 서버를 띄워 `index.html`을 열고, 콘솔 에러·초기 렌더링을 확인.
- 실제 키 입력 자동화가 브라우저 pane에서 `ArrowLeft` 등으로 정상 매핑되지 않는 이슈가 있어(자동화 툴 자체의 키 이름 문제로 추정, 앱 결함 아님), 게임이 실제로 리스닝하는 것과 동일한 `KeyboardEvent('keydown', {key:'ArrowLeft', ...})`를 `window`에 디스패치하는 방식으로 방향키 입력을 재현하여 테스트.
- `touchstart`/`touchend` 이벤트를 디스패치하여 스와이프 입력도 별도로 검증.
- 800회 랜덤 방향키 입력 스트레스 테스트로 게임오버 판정·타일 중복 여부·JS 예외 발생 여부를 검증.
- 승리 오버레이는 실제로 2048까지 플레이하는 대신, `WIN_VALUE`를 일시적으로 8로 낮춰 오버레이 렌더링과 "계속하기" 흐름을 시각적으로 확인한 뒤 즉시 2048로 원복(코드에는 최종적으로 원래 값만 남음).
- `resize_window`로 모바일 뷰포트(375x812)에서 레이아웃을 스크린샷으로 확인.

## 발견한 문제와 수정 내역

### 1. (실제 버그) 병합(merge) 펄스 애니메이션이 동작하지 않음
- `style.css`에는 `.tile-merge` 클래스와 `@keyframes pulse` 애니메이션이 정의되어 있고, spec.md 4.2에도 "병합된 타일: 잠깐 확대 후 축소되는 펄스 효과"가 명시되어 있었다.
- 그러나 `script.js`의 모든 `render()` 호출에서 `mergedSpots` 인자가 항상 `null`로 고정되어 있어, 병합이 실제로 일어나도 `tile-merge` 클래스가 절대 붙지 않는 죽은 코드였다. `move()`/`moveLeft()`/`slideAndMergeRow()` 어디에서도 어느 칸에서 병합이 일어났는지 위치 정보를 추적하지 않았기 때문.
- **수정**: `slideAndMergeRow`가 각 행에서 병합이 일어난 위치를 담은 `mergedMask`를 함께 반환하도록 하고, `moveLeft`가 이를 모아 `mergedMaskBoard`로 반환, `move()`가 방향에 따라 보드를 회전시키는 것과 동일한 방식으로 `mergedMaskBoard`도 함께 회전시켜 원래 좌표계로 되돌리도록 수정했다. `handleMove()`에서 이 마스크를 좌표 리스트(`mergedSpots`)로 변환해 `render(spawned, mergedSpots)`에 전달하도록 변경.
- 브라우저에서 실제 병합을 유도해 확인한 결과, 병합된 타일에 `tile tile-merge` 클래스가 정상적으로 부여됨을 확인.

### 2. (실제 버그, 엣지 케이스) 승리와 게임오버가 같은 수에서 동시에 발생하는 경우 게임오버가 유실됨
- 기존 로직: 한 번의 이동에서 2048 타일이 처음 등장(승리)하면 `showMessage('You Win!', ...)`를 호출하고 즉시 `return`하여, 같은 이동 직후의 `hasAnyMoves()` 게임오버 체크가 아예 실행되지 않았다.
- 만약 바로 그 승리 이동이 동시에 "더 이상 이동 불가"(보드가 가득 참 + 인접 동일값 없음) 상태를 만든 경우, 플레이어가 "계속하기"를 누르면 `isGameOver`가 한 번도 `true`로 설정되지 않았기 때문에 `handleMove`가 계속 정상 진입 → `move()`가 `moved:false` 반환 → 아무 반응 없이 조용히 멈추는 상태가 되고, "Game Over!" 메시지가 영원히 뜨지 않는 소프트락이 발생할 수 있었다. spec.md 3.5는 "매 이동 후 이 조건을 체크"라고 명시하므로 이는 스펙 위반이다.
- **수정**: 승리 여부(`justWon`)와 게임오버 여부(`hasAnyMoves` 결과로 `state.isGameOver`)를 매 이동마다 항상 함께 평가하도록 순서를 변경. 승리 메시지가 우선 표시되더라도 `isGameOver` 플래그는 정확히 세팅되도록 했고, `keepGoing()` 함수도 "계속하기" 클릭 시 이미 게임오버 상태라면 즉시 "Game Over!" 메시지를 다시 띄우도록 보강했다.
- `WIN_VALUE`를 8로 낮춘 테스트에서 "You Win!" → "계속하기" 클릭 → 이후 정상적으로 이동이 계속 반영됨을 확인했다(일반적인 케이스는 영향 없음을 확인).

### 3. (경미) 사용하지 않는 코드 정리
- `boardsEqual()` 함수가 정의되어 있었지만 어디에서도 호출되지 않는 죽은 코드였다(이동 여부 판정은 이미 `slideAndMergeRow` 내부의 배열 비교로 처리됨). 혼동을 줄이기 위해 제거했다.

## 검증 결과 체크리스트 (spec.md 대비)

| 항목 | 결과 |
|---|---|
| 초기 로드 시 타일 2개 생성, 콘솔 에러 없음 | 통과 |
| 방향키(상하좌우) 이동/병합 (rotate 기반 공통 로직 정확성 포함) | 통과 — `rotateClockwise`/`rotateCounterClockwise` 조합으로 4방향 전부 좌표 변환을 직접 추적하여 검증, 브라우저 실동작으로도 재확인 |
| 병합 시 점수 정확히 반영 | 통과 (예: 2+2 병합 → score 4, 이후 중첩 병합까지 누적 정확) |
| 이동해도 변화 없는 입력 시 새 타일 생성 안 됨(스팸 방지) | 통과 — 동일 방향 재입력 시 보드/점수/타일 개수 불변 확인 |
| New Game 클릭 시 점수 초기화, 최고 점수(localStorage) 유지 | 통과 — score 0으로 리셋, `localStorage`의 best 값 유지 확인 |
| 모바일 뷰(375x812)에서 레이아웃 확인 | 통과 — 보드가 뷰포트를 벗어나지 않고 정사각형 유지, 헤더가 세로로 접힘(미디어쿼리 정상 동작) |
| 게임오버 판정 로직 | 통과 — 800회 랜덤 이동 스트레스 테스트에서 보드가 16칸 가득 찬 시점에 정확히 "Game Over!" 표시, 이후 입력 무시됨을 확인 |
| 승리(2048) 판정 및 "계속하기" 흐름 | 통과(수정 후) — 오버레이 표시, 계속하기 클릭 후 정상 진행, 승리+게임오버 동시 발생 엣지 케이스도 수정으로 커버 |
| 터치 스와이프 입력 | 통과 — `touchstart`/`touchend` 디스패치로 좌측 스와이프 시 타일이 정확히 좌측으로 이동/병합됨을 확인 |
| 접근성(aria-label, aria-live, 44px 터치 타겟) | 통과 — 버튼 `aria-label` 부여, 점수판 `aria-live="polite"`, 버튼 `min-height/width: 44px` 확인 |

## 최종 결론
`spec.md` 설계와 요구사항을 대부분 정확히 구현하고 있었으며, 리뷰 과정에서 실제 동작에 영향을 주는 버그 2건(병합 애니메이션 미동작, 승리+게임오버 동시 발생 시 소프트락 가능성)을 발견하여 `script.js`에서 직접 수정했다. 수정 후 재테스트(브라우저 실동작 + 스트레스 테스트)에서 모든 항목이 정상 동작함을 확인했다. 콘솔 에러 없음, 모바일 레이아웃 정상. 이동 슬라이드 애니메이션은 spec.md에 "스트레치 목표(생략 가능)"로 명시되어 있으며 현재 미구현 상태이나 이는 스펙 위반이 아니다.

**결론: 수정 완료 후 정상 동작.**
